# Command lifecycle

- Constructors store arguments and create detached data; they do not edit the document.
- begin captures the previous state and applies any initial edit immediately.
- Every command implements update as undo -> replace input -> redo through
  updatePreview. Validate input before undo; the initial undo snapshot stays fixed.
  Updates after commit or an error are rejected without changing the document.
- commit finalizes the current edit. The next command sees its resulting state.
- finishCommandRecorder closes the recorder and queues history registration.
- CommandManager.execute/update registers already-applied recorders in undoStack.
  It does not execute their commands. Undo/Redo also drain pending registrations.
- CommandRecorder.execute only replays an undone, finished recorder for Redo.
  It calls command.redo in forward order; Undo calls command.undo in reverse.
- Recorder cancellation calls cancel on the active command, then undo on committed
  commands in reverse order. A cancelled recorder is closed and never registered.

Command.cancel is for an uncommitted edit; Command.undo must also work after
commit. CANCELLED may mean a successful no-op and is not treated as ERROR.
Commands returning ERROR from begin must not leave applied edits behind. Undo
and redo must validate before changing state: on ERROR the recorder attempts
to compensate preceding successful commands, and the manager retains the history
entry in its original stack. Compensation itself must be reliable; arbitrary
exceptions or partial mutations inside a failed command cannot be made atomic
by the recorder.

Undo/Redo are ignored while a recorder is open. Empty recorders are not registered
and do not clear redo history. A newly registered edit clears redo history.

EditorAPI emits events at the time of the edit. EventManager retains these across
frame boundaries; UIManager consumes a snapshot using takeEvents before refreshing
widgets. Events generated by that refresh remain pending for the next frame.

Regression tests: node --test tests/commands.test.cjs

## Update inputs

Targets (model/path) remain fixed for the lifetime of a primitive command.
Clear accepts an empty input and reapplies clearing after restoring the array.
Push accepts newElement; Insert accepts insertIndex/newElement; RemoveItem
accepts removeIndex; RemoveItems accepts removeIndices. Indices refer to the
array before begin, not the current preview. Concat accepts newElements.
SetProperty accepts newValue and SetVec2 accepts newVec.

Property targets must use a PropertyRoot: Model, Runtime, State, Editor, Project,
ProjectCache or EditorState. Never use an embedded Vertex, Bone or BoneWeight as
the event source. For example, use the sprite model and
`vertices.<vertexID>.co`, not the vertex and `co`. Model bone and vertex paths
use dictionary IDs directly. Runtime bone targets still resolve their current
array index by ID on each undo/redo; emitted events always contain the owning
root and concrete path.

Translate and BoneExtrude accept total movement since begin. BoneExtrude targets
an armature and parent bone ID; its new child starts at the parent's tail, keeps
the same ID on updates/redo, and is removed on undo/cancel.
WeightPaint accepts paintingWeights: Record<VertexID, number>, the total additive
deltas since begin. Results are clamped to [0, 1]; absent initial weights are zero.
SetActiveObject accepts newActiveObject; SetProject accepts newProjectData.
